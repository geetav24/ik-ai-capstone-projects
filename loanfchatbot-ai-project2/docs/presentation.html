How Project 2 Extends Project 1

Project 1 — LoanFlow AI

  • Form-based — one question per submit
  • One-shot pipeline — no memory
  • Audience: bank loan reviewer
  • LangGraph — deterministic 8-agent pipeline
  • Full review: Risk + Fraud + DocCheck + Eval
  • Tools via MCP server (HTTP SSE)
  • Input + Output guardrails

Project 2 — LoanInquiry AI

  • Chat-based — multi-turn conversation
  • BufferMemory + SummaryMemory across turns
  • Audience: loan applicant / general user
  • LangGraph and Google ADK — compare both
  • Policy · Status · Eligibility · Web search
  • Tools as direct Python functions
  • Input guardrail only (injection hard-stop)

⚡ Shared infrastructure: same Pinecone index, same SQLite DB, same .env (+ TAVILY_API_KEY). Project 1's backend does not need to be running — Project 2 reads data sources directly.

Two Pipeline Implementations — Learn the Contrast

LangGraph v2

  • Explicit graph edges written in Python code
  • Every routing decision is visible in code
  • 7 nodes · 2 conditional edge functions
  • _route_from_intent() + _route_from_policy()
  • Deterministic — same input → same route every time
  • Best for: audit trails, regulated systems

Google ADK

  • Write description strings on each sub_agent
  • Triage LLM reads descriptions and decides
  • triage_agent + 4 specialist sub_agents
  • LiteLlm bridge → OpenAI (no Gemini key needed)
  • Routing is implicit — LLM's language understanding
  • Best for: conversational routing, quick prototyping

"LangGraph — you draw the edges.   ADK — the LLM reads descriptions and decides."
Project 2 ships both so you can run them side-by-side and see the tradeoffs.

# ADK: less code, declarative _triage_agent = LlmAgent( name="loan_inquiry_triage", model=LiteLlm("openai/gpt-4o-mini"), instruction="Route to exactly one specialist based on intent...", sub_agents=[_policy_agent, _status_agent, _web_agent, _eligibility_agent], )

Eligibility maps to ["policy", "eligibility"] — two specialists in sequence. PolicyAgent must run first to fetch DTI limits and credit tiers from Pinecone, then EligibilityAgent applies those rules to the user's stated financials.

Specialist Agents

PolicyAgent Pinecone RAG

  • Strips <<<USER_MESSAGE>>> delimiters before embedding
  • Calls search_policy(query, top_k=5)
  • Retrieves only — no answer generation
  • SynthesisAgent sees raw chunks and cites them

StatusAgent SQLite

  • Reads state["loan_id_hint"] from IntentRouter
  • Calls get_loan_status(loan_id) → shared loanflow.db
  • None-safe: "loan ID not found" → polite message
  • Returns full LoanStatus dict

WebSearchAgent Tavily

  • Calls web_search(query) → Tavily REST API
  • Returns top-3 WebResult dicts (title · URL · content)
  • Requires TAVILY_API_KEY in .env
  • Used for external resources not in policy KB

EligibilityAgent LLM

  • Runs after PolicyAgent — needs policy_chunks
  • LLM extracts income / credit score from message
  • Applies DTI, LTV, credit-tier rules from policy context
  • Returns EligibilityResult: eligible, max_loan_amount, reason, citations
  • Falls back to safe default on non-JSON LLM response

SynthesisAgent — The Final Answer

Reads ALL specialist outputs. Builds context sections (policy citations · status summary · web results · eligibility conclusion). If injection_signals non-empty: adds a security note telling the LLM not to follow embedded instructions. If no specialists ran (general intent): answers conversationally from context alone. Calls ask_llm_fast.

Memory System — Handling Multi-Turn Conversations

BufferMemory

  • Stores last N messages verbatim (default: 10)
  • Sliding window — oldest dropped when full
  • Fast — zero LLM cost
  • Loses old context after N turns
  • Best for: short conversations, latency-critical
format_for_prompt() →
"User: ...\nAssistant: ..."

SummaryMemory

  • Stores: summary paragraph + last N verbatim messages
  • Trigger: when buffer exceeds recent_messages × 2
  • Compresses oldest half → 2-3 sentence summary via ask_llm_fast
  • Keeps conversation coherent across 20+ turns
  • Best for: long conversations, topic continuity
"[Earlier summary]: User asked about...
User: ...\nAssistant: ..."

session_store — In-Process Session Map

Module-level dict: session_id → BufferMemory | SummaryMemory. get_or_create(session_id, memory_type) creates on first call. Production note: replace with Redis — redis_client.setex(session_id, 3600, pickle.dumps(memory)). Interface stays the same.

⚠️ Two memory systems coexist: ADK's InMemorySessionService (LLM-facing history managed by ADK) and our session_store (for memory_snapshot in the API response). DELETE /chat/{sid} only clears session_store — not ADK's internal session.

3 Defenses in Order

  • ① Length cap — reject if > 2000 chars → HTTP 400
  • ② Financial PII regex — SSN · bank account · credit card
  • ③ Presidio — PERSON · EMAIL · PHONE · LOCATION (scoped)
  • ④ Injection denylist — 34 phrases across 5 categories
  • ⑤ Delimiter wrap — <<<USER_MESSAGE>>>

Key Improvement Over Project 1

  • Presidio entity scope is restricted
  • US_BANK_NUMBER excluded from Presidio
  • Its numeric pattern (\d{8,17}) collides with dollar amounts like $12,000,000
  • Regex uses negative lookbehind: (?<!$)\b\d{8,17}\b
  • Scans only the message (no structured app fields like P1)

🛡️ The injection hard-stop happens in main.py BEFORE calling the ADK runner. Zero LLM calls are made for injected messages — not even the guardrail prompt.

No MCP Server (vs Project 1)

Project 1 uses a standalone MCP server (FastMCP over HTTP SSE) so tools run in a separate process. Project 2 calls tools as plain async def functions — simpler, same process, no SSE transport needed. The tradeoff: less decoupling, but faster setup and easier to debug.

Shared Pinecone Index

Both projects use loanflow-ai index with text-embedding-3-small. Run Project 1's generate_policy.py once — Project 2 reads those embeddings directly. No double-indexing, no drift between copies.
